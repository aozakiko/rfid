## 0. 一页结论

当前仓库已经不是一个“想法原型”，而是一个具备 Web 界面、LLM 生成、协议验证、自动迭代、实验产物和审计记录的完整原型平台；现有单元测试也能够通过。下一阶段最值得投入的，不是继续增加页面或把“AI + RFID”作为口号，而是把工作收敛为一个可验证的研究问题：

> **面向多维统计任务，研究一种由结构化协议基因、验证器反馈和多目标评价共同驱动的 RFID 协议自动演化方法，并验证“一次匿名聚合、多个统计结果、自适应复核”的协议，能否在准确率基本不降的前提下降低通信开销并提升复杂分布下的鲁棒性。**

建议把项目题目和答辩主线统一为：

> **面向多维统计任务的可验证自适应 RFID 协议演化平台**

这条主线的优势是：继承现有平台资产，补上目前最关键的科研闭环，且三个人可以并行贡献，最终同时得到算法、实验和系统三类成果。

### 1.2 当前工作的实质

目前最成熟的工作是“**协议候选代码的生成与平台化管理**”，已经有：

1. 父代协议读取与组合；
2. LLM 交叉、突变和自修复；
3. 代码级验证与基础任务烟测；
4. 多代协议、图表和审计记录；
5. Web 端查看和操作。

因此，下阶段不应从零重做系统，而应把“自优化”从**代码生成流程**升级为**有适应度、有基准、有消融、有谱系、有多目标取舍的可验证演化系统**。

### 1.3 申报设想与当前实现之间的主要缺口

| 申报/文档中的设想 | 当前实现的实际情况 | 下阶段处理建议 |
|---|---|---|
| 多维统计任务 | `test/Task.py` 和 `Test.py` 仍以价格众数为主线，连续统计任务缺少统一成套场景和对照实验 | 只保留 3 个核心任务做深：众数/Top-k、均值与方差、基数；中位数/分位数作为扩展 |
| 遗传算法或进化计算 | 当前更接近“父代两两交叉 + LLM 重写 + 验证修复”；自动迭代的父代组合开始时已固定，新子代没有可靠地按 fitness 回流父代池 | 增加结构化基因、适应度、Pareto 档案或锦标赛选择，再称为进化方法 |
| 三重正确性验证 | 物理约束主要检查帧长和时隙宽度；信息隔离是文本启发式扫描，告警不会阻止任务成功，且会漏掉 `tag.__dict__.get("price")`、别名等访问 | 将信息隔离由构造、AST/污点分析和运行时观测共同保证，并设为成功门禁 |
| 性能优化 | 大量结果使用协议自报的模拟时间，系数由 Python 代码设定，不能等同真实 RFID 链路时延 | 主指标改为 reader bits、tag bits、slots、frames、rounds；CPU 时间只作次要指标 |
| 鲁棒性 | `test/Task.py` 的随机种子和参数固定；协议中使用 Python 内建 `hash()` 会受进程哈希种子影响；敏感度脚本主要汇总 `avg_time_s` | 固定并记录所有 seed，替换非确定性 hash，引入盲测分布、准确率/误差和置信区间 |
| Vue + FastAPI + WebSocket + C/C++ 导出 | 当前主要是标准库 HTTP 服务和静态 HTML/CSS/JS，未见完整上述技术栈 | 不建议仅为“架构创新”重写；除非验收明确要求，否则保留现栈并把精力放在算法与实验 |
| “显著提升” | `rfid/周报1.pdf` 一方面写“提升并不明显”，结论又写“显著提升”；部分 CSV 对同一协议给出不同准确率，部分子代明显变慢 | 统一口径：只写已经由同口径实验支持的结论，失败结果也要如实展示 |

---

### 1.4 下阶段前必须先修的三类“证据红线”

1. **正确性口径**：`Test.py` 当前允许估计众数集合是真值子集即算命中，会掩盖漏报；必须改为 F1/recall 等完整口径。
2. **确定性**：协议和场景中若使用 Python 内建 `hash()` 或未固定随机种子，同一代码不同进程可能得到不同结果；所有随机源必须显式传入 seed，哈希改成稳定实现。
3. **运行边界**：LLM 生成的 Python 当前在 Web 服务进程内 `importlib` 执行，存在任意代码执行风险；下阶段至少放入隔离子进程，并设置超时、资源限制和白名单导入。

这三项不是附加工程，而是“创新实验结论可信”的前置条件。

## 2. 创新点筛选

### 2.1 推荐的主创新：可验证、多目标、面向多统计任务的协议演化

**研究问题**

在不直接读取单标签私有属性、并受帧长/时隙宽度等物理约束时，能否自动演化出一种 RFID 匿名聚合协议，使其同时支持多个统计任务，并在准确率、通信开销、鲁棒性和验证成功率之间取得更优 Pareto 解？

**相比当前工作的新意**

- 从“LLM 写出一段可运行代码”升级为“LLM 修改结构化协议基因，平台编译、仿真、验证、淘汰并保留谱系”；
- 从“单任务、单分布、单指标”升级为“多任务、多分布、误差 + 通信 + 鲁棒性 + 生成质量”；
- 从“验证后判断是否通过”升级为“验证器反馈参与下一轮演化”；
- 从“展示生成了哪些协议”升级为“解释哪个基因、哪个验证阶段、哪个分布贡献了性能”。

### 2.2 次级创新 A：任务参数化的多统计协议编译器与共享统计草图

先把 `count/mode/sum/mean/variance/cardinality/set-difference` 等统计目标定义成任务算子，再编译到共享测量原语：同一组匿名帧尽量同时服务多个统计量，而不是为均值、方差、基数分别执行完整协议。

可研究的机制包括：

- 哈希桶/计数草图：支持基数和频次；
- 位图或零槽估计：支持众数、Top-k；
- 值域分桶和随机投影：支持均值、方差；
- 置信度驱动的候选复核：只对不确定性高的候选增加帧。

**核心假设 H1**：在相近误差下，任务编译和共享统计草图的总通信开销低于分别运行多个单任务协议，并且任务切换无需重新发明一套自由 Python 协议。

### 2.3 次级创新 B：不确定性驱动的自适应早停与复核

现有 `test/generation_3/test_g3_1.py` 已包含融合分数、置信差、候选复核和单值重检的雏形。可把它从某个生成协议中的偶然机制，提升为所有候选协议共享的正式策略：

- 置信差大：早停，不再增加帧；
- 置信差小：只对 Top-k 候选做值映射复核；
- 仍不确定：对最可疑候选做单值或小批精确复检；
- 输出结果同时给出置信度和建议复核次数。

**核心假设 H2**：与固定轮数复核相比，自适应复核能在相同准确率下减少通信开销，或在相同开销下提高准确率。

### 2.4 次级创新 C：验证反馈驱动的 LLM 协议演化

当前 Prompt 是父代代码加任务说明。下一版应把验证结果作为结构化反馈：

```text
任务 -> 选择父代 -> LLM 生成结构化子代 -> 编译/运行
     -> 逻辑、物理、信息隔离、任务指标验证
     -> 失败原因和成本反馈 -> 定向修复/选择 -> Pareto 档案
```

对比条件至少包括：

1. 单次 LLM 生成，不验证修复；
2. LLM 随机交叉；
3. 适应度选择 + LLM 交叉；
4. 适应度选择 + 验证反馈修复（拟议方法）。

**核心假设 H3**：验证反馈能提高可执行率、约束通过率和最优候选质量，而不是只提高代码“看起来像协议”的比例。

### 2.5 方法型创新 D：可复现的 RFID 统计协议基准与成本模型

这是支撑前三项创新的基础工作，也适合写进论文方法部分。

建议同时报告：

- 正确性：Top-k F1、均值/方差/基数相对误差；
- 通信：reader bits、tag bits、总时隙、帧数、交互轮数；
- 鲁棒性：不同分布、规模、缺失率、噪声下的均值、P95 和最坏值；
- 生成质量：首次生成成功率、修复后成功率、约束通过率、LLM 调用数、token 成本、谱系深度；
- 计算：Python CPU 时间，仅作为实现效率参考。

### 2.6 信息安全与可信性创新 E：可证明的信息隔离与属性隐私

不建议继续把“信息隔离”只写成扫描字符串。可分三层：

1. **结构层**：协议基因中显式区分标签侧响应算子和读写器侧决策算子；
2. **编译层**：只允许白名单算子生成可执行协议，禁止任意属性读取；
3. **运行层**：对标签侧可见数据和读写器侧可见数据分别插桩，验证读写器决策没有依赖单标签私有值。

还可以加入影子执行：交换标签私有属性但保持聚合信号，检查读写器决策是否变化；用别名、`getattr`、反射、闭包等对抗样例测试扫描器。这会把当前的“启发式通过”升级为可度量、可攻击验证的安全属性。

### 2.7 候选创新优先级

| 优先级 | 创新点 | 价值 | 风险 | 建议 |
|---|---|---|---|---|
| P0 | 可验证多目标协议演化 | 直接构成论文核心方法 | 工作量大，需控制任务数量 | 必做 |
| P0 | 共享统计草图/一次采集多指标 | 与项目“多维统计”主张高度一致 | 算法设计难度较高 | 必做，先覆盖均值、方差、基数 |
| P0 | 可复现基准和通信成本模型 | 决定结论是否可信 | 需要重构测试口径 | 必做 |
| P1 | 不确定性驱动复核 | 已有代码雏形，落地性价比高 | 参数敏感 | 必做 |
| P1 | 验证反馈驱动修复 | 可形成清晰消融 | LLM 成本与稳定性 | 必做 |
| P0 | 可证明的信息隔离 | 直接关系项目隐私主张，现有扫描容易漏报 | Python 动态性带来分析难度 | AST/污点 + 影子执行，至少实现一种 |
| P2 | 协议谱系与可解释性 | 平台展示效果好 | 易变成纯 UI 功能 | 只做轻量版 |
| P2 | 中位数/分位数、缺失盘点 | 场景丰富 | 范围膨胀 | 作为扩展，不进入主线承诺 |

## 3. 推荐的研究假设和评价门槛

以下是“立项阶段的验收门槛”，不是预先承诺的实验结果。

### H1：多统计共享优于多协议串联

- 对比对象：拟议共享协议，vs. 三个单任务协议依次执行；
- 任务组合：均值 + 方差 + 基数；众数/Top-k 可复用频次信息；
- 目标门槛：相对通信总开销降低至少 15%，均值相对误差不超过 5%，方差相对误差不超过 10%，基数相对误差不超过 5%；
- 失败也可报告：若共享结构误差增加过多，给出准确率—通信开销 Pareto 曲线，不强行宣称更优。

### H2：自适应复核优于固定复核

- 对比对象：固定 2/3/4 轮复核、无复核、拟议不确定性驱动复核；
- 目标门槛：在准确率差异不超过 1 个百分点时，通信开销降低至少 20%；或同等开销下准确率提高至少 2 个百分点；
- 必须展示不同置信阈值的敏感性。

### H3：验证反馈提升 LLM 演化质量

- 对比对象：单次生成、随机交叉、适应度选择、适应度选择 + 验证修复；
- 目标门槛：约束通过率或可执行率提高至少 15 个百分点，且最优候选通信开销不低于基线；
- 同时报告 LLM 调用数和 token 成本，避免只谈质量不谈成本。

## 4. 技术路线与共同接口

### 4.1 目标流程

```text
自然语言/参数
   -> TaskSpec（任务、分布、规模、约束）
   -> 协议基因库/结构化 ProtocolGenotype
   -> LLM 交叉、变异、定向修复
   -> 编译为可执行 Python 协议
   -> 仿真运行 + 逻辑/物理/信息隔离验证
   -> EvaluationReport（误差、通信、鲁棒性、成本）
   -> Pareto 档案 + 选择/淘汰 + 谱系
   -> Web 实验面板与论文图表
```

### 4.2 四个必须冻结的共同接口

1. **TaskSpec**：任务类型、值域、分布、标签数、缺失率、随机种子、误差约束、通信约束。
2. **ProtocolCandidate**：候选 ID、父代、基因、Prompt、模型版本、源码、参数、生成状态。
3. **RunResult**：真值、估计值、reader bits、tag bits、slots、frames、rounds、CPU 时间、随机种子。
4. **EvaluationReport**：误差、正确性、通信、鲁棒性统计、验证状态、失败原因、置信区间。

接口应以 JSON Schema 或 dataclass + 单元测试冻结。三个人只通过这些接口协作，避免共享内部实现。

### 4.3 建议的目录边界

```text
rfid/code_add/
├─ task_spec/          # 任务与分布定义（共同接口，谨慎修改）
├─ stat_protocols/     # 共享统计草图、均值/方差/基数/Top-k 协议
├─ evolution/          # 基因、适应度、选择、LLM 修复、Pareto 档案
├─ benchmark/          # 种子、场景、成本模型、统计分析、盲测集
├─ validation/         # AST/运行时隔离、物理约束、语义验证
├─ course_project/     # 现有 Web 平台，只做集成和展示
└─ Experiments/        # 论文图表和结果，不放核心逻辑
```

### 5.4 严枭：验证、平台与工程集成负责人

## 7. 实验设计

### 7.1 任务矩阵

| 类型 | 主任务 | 扩展任务 |
|---|---|---|
| 离散频率 | 众数/Top-k | 多峰、并列众数 |
| 连续统计 | 均值、方差 | 中位数/分位数 |
| 规模统计 | 基数 | 缺失率、缺失桶 |
| 复合任务 | 均值 + 方差 + 基数共享采集 | 加入 Top-k，统计复用收益 |

### 7.2 数据分布

至少覆盖：

- 单峰；
- 多峰；
- 高斯；
- 长尾/幂律；
- 均匀；
- 缺失/遮挡；
- 极端值/噪声；
- 标签规模 1k、10k、100k。

每个实验点使用独立 seed，建议至少 20 个 seed；若计算资源不足，先做 10 个 seed，但必须报告 95% 置信区间。

### 7.3 对照组

1. Polling/逐标签读取；
2. 全识别后计算；
3. 现有最优单任务协议；
4. 多个单任务协议串联；
5. LLM 一次生成；
6. LLM 随机交叉；
7. 适应度选择；
8. 适应度选择 + 验证修复；
9. 固定复核；
10. 拟议自适应复核。

### 7.4 指标定义

- 众数/Top-k：precision、recall、F1、Jaccard、Top-k 命中率；严禁只用 `estimated.issubset(true)` 作为唯一正确性；
- 均值/方差/基数：相对误差和绝对误差；
- 通信：reader bits、tag bits、slots、frames、rounds；
- 鲁棒性：不同分布下均值、P95、最坏值；
- 演化：首次通过率、最终通过率、修复轮数、API/token 成本；
- 可信性：随机种子、源码 hash、Prompt hash、模型版本、验证报告齐全率。

### 7.5 必做消融

- 去掉适应度选择；
- 去掉验证反馈修复；
- 去掉共享草图；
- 去掉自适应复核；
- 去掉信息隔离约束；
- 改变置信阈值；
- 改变父代池规模。

## 9. 风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| 创新点过多 | 同时做 GRDL、Vue、FastAPI、C/C++、很多统计任务 | 冻结为 3 任务 + 1 核心演化方法，其余标为扩展 |
| LLM 不稳定 | 同一 Prompt 结果不同、生成代码不可运行 | 固定模型/Prompt 版本，缓存结果，多 seed 复跑，记录 token 和失败 |
| 评价被“钻空子” | 协议只输出候选子集或使用弱命中规则 | 严格 precision/recall/F1/误差，设盲测集，避免 `subset` 就算全对 |
| 虚假时间优势 | 自定系数让某些协议自动更快 | 以通信量为主，真实 CPU 时间单列；如无硬件，不声称 EPC C1G2 真实时延 |
| 数据不独立 | 多次运行同一数据 | 每个 seed 独立生成并记录，测试/调参/盲测分离 |
| 集成冲突 | 三个人同时改协议、实验、Web | 目录所有权、冻结接口、每周一次集成日 |
| 成果虚高 | 申报书已有较强表述，但实验尚不足 | 论文和答辩只写可证明内容，保留局限性 |
| 时间表冲突 | 申报材料中的项目周期与当前日期/计划不一致 | 以当前 10 周冲刺为执行计划，并在结题材料中统一时间口径 |

## 3. 当前自优化流程

```text
选择 RFID 任务、场景和初始父代
  → 严格验证并评价父代
  → 将父代源码、任务约束和开发集评价摘要交给模型
  → 生成子代，按已有流程验证/修复
  → 在同一开发集评价子代
  → 父子合并比较，保留较优候选
  → 更新后续父代并继续生成
  → 保存每轮评价、选择决定和源码快照
```

目前实现的是**质量反馈驱动的候选池更新**：

- 集合任务使用 F1 作为连续质量分数，完整集合相等才算答案通过。
- 数值任务质量分为 `1 / (1 + abs(estimate - truth) / max(abs(truth), 1))`；另按验证器的相对/绝对容忍度记录通过率。
- 排序先比较答案通过率，再比较质量分数；不把自报零耗时当作优化。
- 候选必须通过严格执行、隔离、物理参数及输出契约等硬性检查，且存在可评价真值，才参与质量排名。答案尚未全部达标的候选可以作为搜索中的中间方案，不能因此被称为已完成优化。
- 初始协议库若与严格模式不兼容，可暂时保留未排名父代作为源码素材；它们不被标记为严格验证通过。
- 自定义任务缺少统一真值时，只进行生成，不自动质量排名。缺失盘点场景没有缺失 ID 真值时同样无法获得有效质量排名。

固定开发集会参与反馈，因此结果不能当作独立盲测。后续效果验证应另外冻结候选、使用没有参与选择的数据。

## 4. 页面使用

### 4.1 自动迭代

在“自动迭代”页选择任务、场景和父代，设置轮数、每候选评价次数、起始 seed 及属性值域。默认启用“按质量更新父代”。

真实生成仍使用当前页面填写的模型配置。预览只生成 Prompt，不调用模型、不执行评价和选择。历史命名已存在时需要更换前缀，以保留旧候选。

结果表显示子代是否保留、答案通过率与质量分数，并可查看最终父代池和完整评价/选择记录。

### 4.2 候选公平比较

在“验证沙箱”页使用上方的任务、场景、安全模式、seed、标签数、值域和重复次数，在“候选公平比较”中填写待比较协议。支持逗号分隔与通配符，可以把生成候选和基础协议一起比较。

后台异步执行，完成后显示质量排名、答案通过率、质量分数和判定。严格检查未通过、没有真值或使用兼容模式的协议不获得严格质量排名，但保留诊断结果。

### 4.3 受限统计候选的配置运行

原配置字段保持兼容，可选新增：

```json
{
  "protocols": ["shared_sketch", "llm_random"],
  "llm_candidate": {
    "candidate_id": "实际候选 ID",
    "model": "实际模型名",
    "prompt_hash": "实际 Prompt hash",
    "response_hash": "实际响应 hash",
    "genotype": {
      "operator": "anonymous_histogram",
      "rounds": 3,
      "slots_per_value": 128,
      "threshold": 1.75
    }
  }
}
```

以上为字段示意，需加入完整实验配置；真实使用时导入已有候选记录，不能用示意身份伪造模型调用证据。runner 会冻结 `llm_candidate.json` 并记录 SHA256。

## 5. 产物和追溯

自动质量迭代保存至：

```text
<场景>/outputs/optimization_runs/<运行 ID>/
  run.json
  Task.source.txt
  <协议>.source.txt
  <协议>.evaluation.json
```

`run.json` 保存评价配置、初始/最终父代、每轮父代、选择决定及相关文件 hash。每份评价报告含 dataset hash、源码身份、验证阶段和逐次结果。运行中检测到参与评价的源码或 Task.py 改变，会中止选择并保留失败状态；模型请求失败也保留已完成评价。

单独比较保存在 `<场景>/outputs/candidate_comparisons/<运行 ID>/comparison.json`。这些场景 outputs 可从平台文件预览和下载。模型密钥不写入本轮运行记录。
